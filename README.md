Проект с домашними заданиями по курсу "Управление ML-продуктом на всех этапах жизненного цикла"

# Установка и запуск

1. Склонировать проект `git clone https://github.com/adalarf/ml_product_management.git`
2. Установка окружения `make setup`
3. Проверка кода `make check`

Нужны `uv`, `make` и Docker (с Docker Compose).

Среда выполнения — Linux/macOS; в Windows используйте WSL. Python 3.12 выбирается
через `.python-version`, зависимости устанавливаются из `uv.lock`.

# Данные

Датасет CIFAR-10. Сырой архив лежит в S3 без изменений, обработанный датасет собирается из него одной командой и выкладывается обратно в S3 под версией.

## Хранилище

```
make s3-up      # поднять хранилище (RustFS) и создать бакет
make s3-down    # остановить (данные остаются в volume)
```

Перед первым `make s3-up` создайте `.env` из примера: `cp .env.example .env` (при необходимости поменяйте значения).
Логин, пароль, адрес и имя бакета берутся из `.env`

Посмотреть содержимое:

- веб-консоль RustFS: <http://localhost:9001> (логин и пароль: `S3_ACCESS_KEY` и `S3_SECRET_KEY` из `.env`);
- AWS CLI: `AWS_ACCESS_KEY_ID=<S3_ACCESS_KEY> AWS_SECRET_ACCESS_KEY=<S3_SECRET_KEY> aws --endpoint-url http://localhost:9000 s3 ls s3://ml-product-management/ --recursive`.

Данные хранятся в именованном volume `rustfs_data` и переживают `make s3-down` и повторный
`make s3-up`

## Как запускать

```
make setup      # окружение
cp .env.example .env   # настройки S3 (один раз)
make s3-up      # хранилище и бакет
make ingest     # скачать архив CIFAR-10 с сайта и положить в S3 (raw/)
make data       # весь конвейер обработки, выгрузка версии v1 в S3 (processed/)
```

## Шаги конвейера

| Make-цель | Команда | Что делает |
|---|---|---|
| `make ingest` | `mlpm-ingest` | скачивает архив с сайта через torchvision и кладёт в S3 `raw/` (существующий объект не перезаписывается) |
| `make download-from-s3` | `mlpm-download-from-s3` | скачивает сырой архив из S3 в `data/raw/` |
| `make convert-to-safe` | `mlpm-convert-to-safe` | pickle -> PNG + JSON-разметка в `data/interim/cifar10/` |
| `make partitioning` | `mlpm-partitioning` | стратифицированное разбиение train/val (раздел `partitioning`) |
| `make stats` | `mlpm-stats` | среднее и std по каналам (только train) в `stats.json` |
| `make export-to-s3` | `mlpm-export-to-s3` | выгрузка версии в S3 `<prefix>/<version>/` из раздела `export` в `configs/s3.yaml`, по умолчанию `processed/cifar10/v1/` |

`make data` выполняет шаги с `download-from-s3` по `export-to-s3`. Переменная Makefile
`ENV_FILE` задаёт файл с настройками S3 (по умолчанию `.env`).


## Что лежит в S3

Бакет `ml-product-management` (имя из `S3_BUCKET`):

```
raw/
    cifar-10-python.tar.gz          # исходный архив, как скачан с сайта
processed/cifar10/v1/
    images/                         # PNG: train_00000.png ... test_09999.png
    annotations/
        train.json                  # 45 000 изображений
        val.json                    # 5 000 изображений
        test.json                   # 10 000 изображений
    stats.json                      # mean и std по каналам (только train)
    manifest.json                   # число изображений, размеры и sha256 файлов,
                                    # параметры (размер валидации, seed), git-коммит
```

## Карточка датасета

- **Источник:** CIFAR-10, <https://www.cs.toronto.edu/~kriz/cifar.html>,
  Python-версия `cifar-10-python.tar.gz`
- **Размер:** 60 000 цветных изображений 32×32, 10 классов, 6 000 на класс; 50 000 в исходном train и 10 000 в test.
- **Классы:** airplane, automobile, bird, cat, deer, dog, frog, horse, ship, truck.
- **Формат после обработки:** PNG, RGB, 8 бит на канал; разметка в JSON (`image_id`, `file_name`,
  `label`, `label_name`, `sha256`).
- **Разбиение:** из исходного train выделена валидация 5 000 (по 500 на класс), в train остаётся 45 000 (по 4 500 на класс); стратификация по классам, seed 42. Исходный test не меняется.
Изображение при разбиении сохраняет свой `image_id` (`train_...`), меняется только файл разметки.
- **Известные проблемы:**
  - низкое разрешение (32×32);
  - в тестовой выборке есть почти-дубликаты обучающих изображений (по оценке авторов ciFAIR, порядка 3%), поэтому метрики на test могут быть слегка завышены;
  - данные не в git: каталог `data/` в `.gitignore`, источник правды — S3.

# Эксперименты

MLflow 3.16.0 хранит метаданные в PostgreSQL, артефакты — в отдельном бакете `mlflow`
того же RustFS. Образы и зависимости зафиксированы. Обучение идёт на CPU; CUDA и
предобученные веса не нужны. Каждый запуск выполняется в отдельном контейнере.
Передача артефактов идёт через MLflow: presigned/multipart-режим отключён, поскольку
внутреннее имя `rustfs` недоступно SDK и браузеру на хосте.
Для контейнера MLflow, запущенного до этого изменения, настройки вступят в силу
после следующего `make infra-up`. До обновления сервера SDK на хосте может читать
артефакты с `MLFLOW_ENABLE_PROXY_MULTIPART_DOWNLOAD=false`.

## Запуск с нуля

```bash
make setup
cp .env.example .env  # один раз; для существующего .env добавьте новые поля из примера
make infra-up
make ingest
make data            # только если processed/cifar10/v1/ ещё нет в S3
make train CONFIG=configs/smoke.yaml
make experiments CONFIG=configs/grid.yaml
make check
make test
make infra-down
```

Повторный `make data` отклоняет существующую версию; это ожидаемое поведение ДЗ №2.
MLflow: <http://localhost:5000>, RustFS: <http://localhost:9001>.
Пароль PostgreSQL и ключи S3 задаются в `.env`; для пароля PostgreSQL используйте
буквы, цифры, `_` и `-`, чтобы он подходил для URI подключения.
`ENV_FILE=путь` выбирает другой файл окружения во всех новых Make-командах.

`make infra-up` собирает образы с текущим git SHA. После изменения исходников
повторите эту команду перед обучением. Коммит и dirty-флаг записываются в каждый run.
Обычный `infra-down` сохраняет S3, PostgreSQL и кеш датасета в именованных volumes.
Для независимой проверки задайте `COMPOSE_PROJECT_NAME=mlpm-hw3-check` перед всеми
командами; `S3_PORT`, `S3_CONSOLE_PORT`, `MLFLOW_PORT` в отдельном env-файле позволяют
избежать конфликта портов с уже работающим проектом.

## Конфиги и выбор модели

- `configs/baseline.yaml`: линейный классификатор над 3072 пикселями.
- `configs/simple_cnn.yaml`: два блока Conv/ReLU/MaxPool, каналы `[32, 64]`,
  классификатор с промежуточным слоем 128.
- `configs/grid.yaml`: пути к baseline и CNN относительно самого файла сетки,
  декартово произведение `train.lr` × `train.batch_size`, настройки финального запуска.
- `configs/smoke.yaml`: одна эпоха маленькой CNN на 100 train-изображениях для проверки связности.

Для новой конфигурации меняйте YAML, а затем запускайте
`make train CONFIG=путь.yaml`. Make добавляет уникальное имя запуска.
Прямой вызов `mlpm-train --config путь.yaml` внутри контейнера использует имя из
конфига буквально и отклоняет повторную запись существующих результатов в S3.

```bash
make experiments CONFIG=configs/grid.yaml ARGS=--dry-run  # показать сетку без контейнеров
```

Основная серия: baseline и шесть CNN (lr: `0.0003`, `0.001`, `0.003`; batch size:
`64`, `128`), по 5 эпох, одинаковое стратифицированное подмножество train из 10 000
изображений, seed 42. Изображения нормализуются по `stats.json` исходной версии
данных; val (5 000) и test (10 000) не сокращаются.

После каждой эпохи считаются val loss, accuracy и macro-F1 по всем классам.
Чекпоинт выбирается по минимальному val loss; при равенстве остаётся более ранняя
эпоха. После восстановления лучшего чекпоинта test оценивается один раз.
Победитель сетки выбирается только по лучшему val loss, при равенстве — по порядку
сетки. Он обучается заново 15 эпох на полном train. Финальный запуск использует
другой объём данных и бюджет и отмечается отдельно от сравнения сетки с baseline.

## Результаты и артефакты

В MLflow все восемь запусков серии относятся к `cifar10-hw3`; теги `role` и
`series_id` разделяют baseline/grid/final и повторные серии. Логируются полный
конфиг, S3 URI данных, git SHA, seed, val-метрики по эпохам, время обучения,
лучшая эпоха, итоговые val/test-метрики, manifest, CSV матрицы ошибок val и модель.
Нулевой F1 для отсутствующего класса входит в macro-F1.

Локальные конфиги и результаты находятся в игнорируемом `artifacts/`.
`artifacts/series/<series_id>/summary.csv` и `summary.json` содержат сводку и имя
выбранного запуска сетки. При ошибке контейнера серия останавливается;
уже завершённые результаты сохраняются.

В бакете данных:

```text
models/cifar10-hw3/<run_name>/
    model.pt       # state_dict, архитектура, классы, нормализация, эпоха, конфиг и git
    config.yaml
    metrics.json   # итоговые val/test, время, run_id; записывается последним
```

`model.pt` загружается через `torch.load(path, map_location="cpu", weights_only=True)`;
модель создаётся функцией `training.models.build_model` из сохранённого описания,
затем загружается `state_dict`. Кеш проверяет хеши разметки, статистик и PNG и
восстанавливает отсутствующие/повреждённые файлы. Между запусками полная версия
данных повторно не скачивается.

## Проверки и сдача

`make check` проверяет Ruff, форматирование и строгий mypy без исправления файлов.
`make test` проверяет нормализацию, кеш, выбор подмножества, метрики, лучший
чекпоинт, изоляцию test и оркестрацию серии. GitHub Actions выполняет обе команды
на pull request.

Для сдачи нужны ссылка на репозиторий и PR в `main` с успешными проверками.
Защита `main` настраивается в GitHub: обязательный PR и успешный job `check`.
Веб-интерфейс MLflow локальный; его история сохраняется в volumes.
